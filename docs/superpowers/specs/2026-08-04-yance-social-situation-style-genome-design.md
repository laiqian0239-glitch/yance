# 言策 Social Situation State 与 Style Genome 设计

日期：2026-08-04  
状态：用户已批准设计方向，作为开源加速 PR #19 的正式子设计  
关联：Issue #18、PR #19  
目标：保留言策现有回复风格多样性，并把风格升级为可组合、可追踪、可学习、按联系人和关系动态变化的真人化表达系统。

## 1. 决策摘要

言策不能把“像真人”简化为自然、温暖、幽默等少数书面化模板，也不能用一句“请自然回复”替代真实社交判断。

言策现有的暧昧、俏皮、个性、风骚、挑逗、撒娇、傲娇、毒舌、幽默、克制、直球、冷淡、热烈等风格必须保留。新系统不以一个固定风格覆盖现有能力，而是建立：

1. `SocialSituationState`：描述当前联系人、关系、互动信号、目标、边界和上下文；
2. `StyleGenome`：用一组可组合维度描述本次回复应该呈现的表达方式；
3. `UserStyleProfile`：用户跨联系人的基础表达习惯；
4. `ContactStyleProfile`：用户面对某个联系人的专属表达方式；
5. `StyleEvidence`：用户真实采用、修改、拒绝和后续效果形成的可追溯证据；
6. `StyleCandidateSet`：根据当前情境生成差异明确的候选，而不是固定三种客服式选项。

核心原则：

> 言策不是选择一个固定语气，而是学习用户面对每个人时真实、丰富、有变化的表达方式。

## 2. SocialSituationState

每次回复生成前必须形成一个版本化、可追踪的 `SocialSituationState`。它不是自由文本 Prompt，而是结构化事实与推断集合。

### 2.1 身份与关系

- 当前联系人和 canonical identity；
- 双方是否已确认均为成年人；
- 当前关系类型与阶段；
- 认识时长、互动频率和最近联系时间；
- 关系趋势：升温、稳定、降温、冲突、修复、疏远或重新建立联系；
- 当前亲密边界和已经出现过的昵称、玩笑、暧昧或挑逗强度；
- 对方明确拒绝、不适、回避或降低热度的证据。

### 2.2 当前互动信号

- 上一轮由谁主动；
- 对方当前语气、情绪和回复长度；
- 是否在释放好感、暧昧、挑逗、吃醋、撒娇、冷淡、敷衍或求安慰信号；
- 是否在转换话题、结束话题、试探边界或等待用户推进；
- 对方是否明显降低参与度；
- 最近几轮双方表达强度是否对称。

### 2.3 用户目标

- 推进关系；
- 维持热度；
- 试探；
- 安慰；
- 化解冲突；
- 收回热度；
- 结束话题；
- 保持神秘感；
- 表达需求；
- 直接确认关系或安排见面。

目标必须来自用户选择、当前任务或可验证上下文，不能由模型无依据决定。

### 2.4 表达约束

- 当前适合主动、克制、撒娇、调侃、认真、直球、冷处理或暂不回复；
- 可使用的暧昧、风骚和挑逗强度；
- 禁止触碰的话题、称呼、玩笑和隐私；
- 用户常用语言、方言、标点、表情和消息长度；
- 联系人专属内部梗和称呼；
- 当前消息是否适合立即回复、稍后回复或拆成多条短消息。

## 3. Style Genome

`StyleGenome` 使用连续维度和少量离散特征表达本次回复风格，不把用户限制为单个风格标签。

### 3.1 核心连续维度

每个维度采用 `0..100`，并保存来源与置信度：

- `intimacy`：亲密程度；
- `ambiguity`：暧昧程度；
- `playfulness`：俏皮程度；
- `teasing`：逗弄程度；
- `seductiveness`：风骚程度；
- `provocation`：挑逗程度；
- `cuteness`：可爱与撒娇程度；
- `tsundere`：傲娇程度；
- `sarcasm`：毒舌与反讽程度；
- `humor`：幽默程度；
- `directness`：直球程度；
- `mystery`：神秘与留白程度；
- `warmth`：温度；
- `restraint`：克制程度；
- `emotionalIntensity`：情绪强度；
- `initiative`：主动程度；
- `vulnerability`：袒露真实感受的程度。

### 3.2 表达形态

- `lengthClass`：极短、短、中、长；
- `sentenceFragmentation`：完整句或碎片化短句；
- `emojiDensity`：无、低、中、高；
- `punctuationProfile`：句号、问号、波浪号、省略号和重复标点习惯；
- `messageBurstCount`：一次发送一条或拆成多条；
- `nicknameUsage`：是否使用昵称；
- `questionDensity`：是否提问以及提问数量；
- `responseDelayClass`：立即、自然延迟、刻意收回热度。

系统不能通过故意制造错别字模拟真人，但应允许短句、省略、反问、语气词、停顿、内部梗和自然不完整表达。

## 4. 三层风格权威

### 4.1 UserStyleProfile

描述用户跨联系人的稳定习惯：

- 平均长度；
- 常用标点和表情；
- 是否爱反问、开玩笑、撒娇、使用昵称；
- 直率或含蓄；
- 习惯的暧昧、幽默、毒舌和情绪强度区间；
- 用户明确禁用的表达。

### 4.2 ContactStyleProfile

描述用户面对某个联系人的专属风格：

- 双方常用称呼；
- 已经形成的内部梗；
- 可接受的亲密、暧昧和挑逗上限；
- 双方常用消息长度与节奏；
- 对方喜欢或反感的表达；
- 用户在该联系人面前与基础风格不同的部分。

### 4.3 SituationStyleDecision

这是单次回复的最终 Style Genome，由以下输入计算：

```text
UserStyleProfile
+ ContactStyleProfile
+ SocialSituationState
+ 当前用户目标
+ 近期 StyleEvidence
= SituationStyleDecision
```

不得把单次模型推断直接写回长期档案。长期风格变化必须通过重复证据或用户确认晋升。

## 5. 候选回复策略

候选不固定为“自然、温暖、幽默”。系统根据当前情境选择差异轴，通常生成三个候选：

- 最像用户当前真实表达的候选；
- 在一个相关维度上更进一步的候选，例如更暧昧、更大胆、更坏、更可爱；
- 在风险或关系推进上更克制的候选，例如更短、更冷、更留白。

候选标签由实际差异动态生成，例如：

- 更像我；
- 再暧昧一点；
- 再撩一点；
- 更大胆；
- 更风骚；
- 更俏皮；
- 更可爱；
- 更坏一点；
- 别太油；
- 更短；
- 更冷一点；
- 更温柔；
- 更有个性；
- 换一种说法。

系统不应在每次回复中展示所有风格，只展示与当前情境有意义且差异明确的候选。

## 6. 真人感检查

### 6.1 需要降低的 AI 痕迹

- 过于完整和工整的长句；
- 频繁总结、解释和教育对方；
- 套路化共情；
- 过度礼貌；
- 一次提出多个问题；
- 无依据的正能量；
- 重复对方原话；
- 套路化土味情话；
- 每次相同句式；
- 与用户标点、表情和长度习惯不符；
- 风格强度与对方当前信号不对称。

### 6.2 需要保留的真实聊天特征

- 短句和碎片化表达；
- 省略主语；
- 反问和留白；
- 自然语气词；
- 轻微反差；
- 内部梗和昵称；
- 适度的表情与重复标点；
- 根据关系和情绪变化回复长度、节奏和热度；
- 某些场景只回复几个字或一个表情。

## 7. 边界与安全

暧昧、风骚和挑逗属于关系许可下的情境表达，不是全局人格。

必须执行以下约束：

- 只有双方均确认是成年人时，才允许启用成人向暧昧或挑逗维度；
- 对方出现拒绝、不适、回避、降温或沉默证据时，自动降低相关维度；
- 不帮助用户骚扰、胁迫、欺骗或绕过明确边界；
- 不利用联系人隐私制造“我知道你秘密”的压迫感；
- 不把针对一个联系人的亲密风格错误应用到其他联系人；
- 不在缺少证据时假定恋爱、性或排他关系；
- 任何自动发送模式都必须经过现有发送权限、Outbox 和风险门禁。

## 8. 现有言策风格迁移

现有言策风格不得删除或简化。迁移方式：

```text
现有风格名称          -> StylePreset
现有风格参数          -> StyleGenome 默认范围
现有优质回复          -> StyleExample
用户采用过的回复      -> PositiveStyleEvidence
用户修改后的最终回复  -> PersonalStyleEvidence
用户拒绝的候选        -> NegativeStyleEvidence
联系人专属表达        -> ContactStyleProfile evidence
```

迁移必须保留来源、版本、联系人范围、创建时间和内容哈希，并支持回滚。

## 9. 学习闭环

每次交互可产生以下证据：

- 用户选择哪个候选；
- 用户点击了哪种风格调整；
- 用户对文本做了哪些修改；
- 最终是否发送；
- 对方后续是否积极回应、继续话题、降温或拒绝；
- 用户是否撤回或标记“不像我”。

学习流程：

```text
单次反馈
→ StyleEvidence
→ 联系人范围与置信度检查
→ 离线评价
→ 候选 User/Contact Style Profile 版本
→ 用户确认或晋升门禁
→ 发布新版本
```

不能由单次点击直接永久改变用户人格，也不能让模型无审查地覆盖历史风格。

## 10. 与开源能力的边界

- SillyTavern：提供 Prompt Manager、Persona、World Info、Example Dialogue 和上下文装配能力；
- LangGraph.js：提供回复推理图、候选分支和检查流程；
- Graphiti：提供带时间有效性的联系人、关系和事件上下文；
- ConvoKit：提供互动模式和语言协调特征；
- Langfuse：保存回复 Trace、候选、用户选择和结果；
- Promptfoo：比较 Style Genome、Prompt、模型和 Persona 版本；
- Argilla：用于人工标注和整理高质量风格样本。

上述项目均不能直接成为用户风格、联系人关系或发送结果的最终业务权威。

## 11. 验收标准

该设计实施后必须证明：

1. 现有言策多样风格全部可迁移且不退化；
2. 同一消息可根据不同联系人和关系生成明显不同但合理的回复；
3. 候选风格差异真实，不只是替换几个形容词；
4. 用户点击“更暧昧、更撩、更坏、更短、更像我”等操作后，Style Genome 发生可解释变化；
5. 联系人专属风格不会泄漏到其他联系人；
6. 对方降温、拒绝或关系恶化时，系统会降低亲密和挑逗强度；
7. 用户修改和最终采用能形成可追溯证据，但不会未经晋升永久改写人格；
8. 每次回复可追踪所用 Social Situation State、Style Genome、样例和模型；
9. 真人感检测能够识别至少一组书面化、套路化和油腻表达回归案例；
10. Windows 现有数据迁移、重启和回滚不损坏原有风格配置。

## 12. 非目标

- 不追求让系统欺骗对方相信其正在与真人或特定本人实时交流；
- 不自动向所有联系人使用暧昧或挑逗风格；
- 不通过故意错字和低质量语言模拟真人；
- 不让模型自行定义关系事实或成人状态；
- 不在本设计中改变平台物理发送和 Outbox 权威。
