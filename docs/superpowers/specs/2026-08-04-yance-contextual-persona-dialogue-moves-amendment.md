# 言策情境人格、对话动作与对象适配补充设计

日期：2026-08-04  
状态：用户补充确认，作为 `Social Situation State + Style Genome` 的正式修订  
关联：Issue #18、PR #19  

## 1. 决策摘要

言策的回复能力不能只由“暧昧、俏皮、成熟”等风格词决定。一个真实、成熟的人会根据对象、关系、场合、目的和对方当下状态切换不同表达方式。

因此回复系统正式拆分为五层：

1. `PersonaStance`：本次回复呈现的人格姿态；
2. `StyleGenome`：语气、亲密、俏皮、挑逗等表达维度；
3. `DialogueMovePlan`：本轮对话要做什么，例如共鸣、承接、延伸话题；
4. `AudienceContext`：面对的是谁、是什么关系、属于什么客户或联系人场景；
5. `ResponseShape`：回复长度、消息条数、自然度、标点、表情和节奏。

现有言策全部回复风格必须保留，一项不删。新增能力只能扩展现有风格系统，不能用新的少数标签覆盖旧风格。

## 2. PersonaStance：人格姿态

人格姿态描述用户在当前场合希望呈现出的“这一面”，不是永久人格，也不能由模型无依据固定用户身份。

建议支持以下可组合姿态：

- `mature`：成熟、稳重、有分寸；
- `intellectual`：知性、有见识、表达清晰；
- `soft_feminine`：温柔、小女人感、柔软、愿意示弱；
- `playful_girl`：少女感、活泼、俏皮；
- `confident`：自信、从容、有主见；
- `independent`：独立、不依附、不讨好；
- `big_sister`：姐姐感、包容、会照顾人；
- `mysterious`：神秘、留白、不过度暴露；
- `cool`：清冷、克制、边界明确；
- `warm`：温暖、亲和、容易靠近；
- `sensual`：有女人味、风情、暧昧张力；
- `professional`：职业、可信、清楚但不机械；
- `decisive`：果断、直接、推动事情；
- `vulnerable`：适度脆弱、真实表达需要；
- `humorous`：轻松、有梗、会化解尴尬。

这些姿态允许混合，例如：

```text
成熟 + 温柔
知性 + 俏皮
独立 + 暧昧
姐姐感 + 风情
专业 + 亲和
清冷 + 神秘
小女人感 + 撒娇
成熟 + 直球
```

“小女人感”在系统中是用户可选择、可学习的表达姿态，不是对女性的固定刻板定义，也不能默认施加给所有用户或所有场景。

## 3. StyleGenome：表达风格

保留现有设计中的连续维度，并补充：

- `maturity`：成熟感；
- `femininity`：女性化表达强度；
- `softness`：柔软感；
- `vulnerability`：示弱程度；
- `resonance`：情绪共鸣强度；
- `curiosity`：对对方的好奇程度；
- `topic_expansion`：延伸话题意愿；
- `supportiveness`：支持与安慰程度；
- `professionalism`：职业感；
- `persuasiveness`：说服和推动程度；
- `distance`：社交距离；
- `brevity`：简短程度；
- `spontaneity`：随口、即时感；
- `polish`：语言工整程度，真人聊天通常不宜长期过高。

现有暧昧、俏皮、个性、风骚、挑逗、撒娇、傲娇、毒舌、幽默、克制、直球、冷淡、热烈等风格全部继续作为 `StylePreset` 和维度组合存在。

## 4. DialogueMovePlan：对话动作

“共鸣”和“延伸话题”不是单纯语气，而是本轮对话的功能。每次回复可以选择一个主动作和零到两个辅助动作。

### 4.1 理解与共鸣

- `acknowledge`：承接对方信息；
- `emotional_resonance`：表达情绪共鸣；
- `validate`：认可对方感受或经历；
- `mirror_energy`：匹配对方当前热度和节奏；
- `comfort`：安慰；
- `encourage`：鼓励；
- `celebrate`：一起高兴；
- `share_parallel_experience`：分享相似经历，但不得抢走话题中心。

### 4.2 推进和延伸

- `topic_expand`：延伸当前话题；
- `open_question`：自然提出开放问题；
- `specific_follow_up`：追问一个具体细节；
- `new_angle`：从新角度继续聊；
- `association`：由当前内容自然联想到其他话题；
- `story_invitation`：邀请对方继续讲故事；
- `future_projection`：自然谈到下一次、以后或共同可能性；
- `invite_action`：提出见面、通话或共同活动；
- `callback`：回扣以前的共同话题、内部梗或约定。

### 4.3 关系与氛围

- `flirt`：暧昧或调情；
- `tease`：轻度调侃；
- `playful_challenge`：俏皮挑战；
- `show_interest`：表达关注和好感；
- `soften`：缓和语气；
- `set_boundary`：表达边界；
- `repair`：冲突修复；
- `cool_down`：主动降温；
- `leave_space`：留白，不强行继续；
- `close_gracefully`：自然收尾。

### 4.4 客户与工作沟通

- `clarify_need`：澄清需求；
- `summarize_need`：确认理解；
- `recommend`：提出建议；
- `explain_value`：说明价值；
- `handle_objection`：回应顾虑；
- `build_trust`：建立信任；
- `next_step`：推动下一步；
- `follow_up`：自然跟进；
- `service_recovery`：处理不满和补救；
- `maintain_relationship`：维护长期客户关系。

系统不得每次都使用追问。真实聊天中，有时只需要共鸣一句、接住情绪、开个玩笑或留一点空间。

## 5. AudienceContext：对象与关系适配

每次回复必须明确对象范围，不允许把一个人的专属风格复制给另一个人。

### 5.1 私人关系

- 陌生人；
- 刚认识；
- 普通朋友；
- 好友；
- 暧昧对象；
- 恋人；
- 伴侣或配偶；
- 前任；
- 家人；
- 长辈；
- 晚辈；
- 久未联系的人；
- 发生冲突的人。

### 5.2 工作和客户关系

- 潜在客户；
- 新客户；
- 成交客户；
- 老客户；
- 重要客户；
- 高风险流失客户；
- 投诉客户；
- 合作伙伴；
- 同事；
- 上级；
- 下属；
- 供应商；
- 招聘候选人；
- 社群成员。

客户适配应基于明确业务事实，例如关系阶段、历史沟通、需求、购买记录、语言偏好、响应速度和已授权资料。不得依据敏感属性进行歧视、操纵或未经证实的推断。

### 5.3 对象专属沟通档案

每个联系人可形成版本化的 `ContactCommunicationProfile`：

- 对方偏好的回复长度；
- 是否喜欢直接表达；
- 是否喜欢幽默；
- 是否愿意聊私人话题；
- 常见在线时间；
- 常用语言和称呼；
- 易产生共鸣的话题；
- 不喜欢的话题和明确边界；
- 对问题、建议、安慰和调侃的接受方式；
- 用户面对该联系人时真实采用过的表达方式。

所有内容必须保存来源和证据，推断与事实分开存储。

## 6. 场合适配

同一个人在不同场合应呈现不同侧面：

```text
面对重要客户：成熟 + 专业 + 亲和 + 明确下一步
面对普通客户：自然 + 简短 + 解决问题
面对投诉客户：共鸣 + 承担 + 补救 + 不辩解
面对好友：随意 + 毒舌 + 内部梗
面对暧昧对象：俏皮 + 留白 + 暧昧 + 适度延伸
面对恋人：温柔、小女人感、撒娇或直球，取决于当前情境
面对情绪低落的人：共鸣 + 陪伴，不急于给建议
面对冷淡的人：降低热度 + 缩短回复 + 留空间
面对冲突：成熟 + 清晰 + 不阴阳怪气
深夜聊天：更柔软、更私人，但仍遵守双方边界
工作场合：减少过度暧昧，强调清楚、可信和效率
```

PersonaStance、StyleGenome 和 DialogueMovePlan 都必须由场合共同决定，不能只依据联系人类型。

## 7. ResponseShape：更短、更自然

回复形态独立于语气和对话动作。建议字段：

- `target_characters`：目标字符数范围；
- `sentence_count`：句子数量；
- `bubble_count`：是否拆成多条聊天气泡；
- `fragmentation`：是否允许短句和片段；
- `question_count`：问题数量，默认最多一个；
- `emoji_density`：表情密度；
- `punctuation_style`：标点习惯；
- `spoken_language_level`：口语化程度；
- `explanation_level`：解释程度；
- `directness`：直接程度；
- `pause_and_ellipsis`：停顿和留白；
- `response_timing_hint`：立即、稍后或暂不回复建议。

默认候选必须包含至少一个“更短、更自然”的版本。系统应优先删除不必要的解释、总结、客套和重复，而不是简单截断句子。

## 8. 候选回复策略

不再固定三种书面风格。根据当前状态，从以下方向选择三个差异明确的候选：

- 最像用户本人；
- 更短、更自然；
- 更有共鸣；
- 更会延伸话题；
- 更成熟；
- 更温柔或更有小女人感；
- 更俏皮；
- 更暧昧；
- 更大胆或更挑逗；
- 更知性；
- 更专业；
- 更适合该客户；
- 更克制；
- 更适合收尾；
- 更适合推进下一步。

候选之间必须在对话动作、姿态或回复形态上产生实质差异，不允许只替换几个形容词。

## 9. 用户快捷调整

在保留现有言策风格选择的基础上，增加：

```text
更短
更自然
更口语
更成熟
更知性
更温柔
更有小女人感
更有共鸣
接住她的情绪
顺着聊下去
延伸一个新话题
问得更自然
别一直问问题
更像我
更像我对这个人说话
更适合这个客户
更专业但别太官方
更俏皮
更暧昧
再撩一点
更大胆
别太油
更克制
给对方留点空间
自然结束话题
```

每次调整都转换成结构化变化，例如更新 `PersonaStance`、`StyleGenome`、`DialogueMovePlan` 或 `ResponseShape`，不能仅把按钮文字追加进 Prompt。

## 10. 现有风格完整迁移

迁移前必须从现有言策代码和数据库导出完整风格清单，包括：

- 风格名称；
- Prompt 和参数；
- 适用场景；
- 示例回复；
- 用户自定义风格；
- 联系人专属风格；
- 历史采用和修改记录。

迁移后必须满足：

```text
旧 Style ID 可追踪
旧风格名称保留
旧参数映射到新维度
旧示例继续可召回
旧用户设置不丢失
旧联系人专属规则不串号
旧回复效果可与新系统做回归对比
```

没有完成完整清单和迁移验证前，不得删除、合并或重命名现有风格。

## 11. 学习和成长

学习对象不只包含“用户喜欢哪种语气”，还包括：

- 用户面对不同人的人格姿态；
- 用户在不同场合的风格变化；
- 用户何时只共鸣、何时延伸话题；
- 用户喜欢怎样追问；
- 用户对不同客户的表达方式；
- 用户通常回复多长；
- 用户何时使用多条短消息；
- 哪类表达让对方继续聊天；
- 哪类表达造成降温或拒绝。

学习必须按 `user + contact + relationship + situation` 分层，不能把一次对客户的专业表达错误学习成用户对恋人的长期人格。

## 12. 验收标准

1. 现有言策全部风格完整迁移且无退化；
2. 支持成熟、知性、小女人感、姐姐感、少女感、独立、神秘、职业等可组合姿态；
3. 共鸣、延伸话题、追问、安慰、调情、收尾等成为结构化对话动作；
4. 同一个用户面对恋人、好友、陌生人和不同客户时产生明显不同的合理回复；
5. 同一个联系人处于深夜聊天、工作、冲突、安慰和关系升温场景时回复姿态能够变化；
6. 默认候选中至少一个版本足够短、自然、口语化；
7. “更有共鸣”和“延伸话题”能够改变回复目标，而不只是改语气；
8. 每个客户可以形成独立沟通档案，且不会串到其他客户；
9. 用户调整操作可解释地映射到五层结构；
10. 任何风格和对话动作都受联系人边界、成年状态、业务权限和发送门禁约束；
11. Windows 现有数据迁移后，旧 Style ID、用户设置、联系人专属风格和示例全部可回滚；
12. 回归集覆盖书面化、过长、连续追问、无共鸣、强行延伸、场合不符和对象串用等问题。

## 13. 非目标

- 不把成熟女人定义成单一形象；
- 不将“小女人感”默认绑定到任何性别或所有场景；
- 不强制每条回复都延伸话题；
- 不强制每条回复都产生问题；
- 不用客户分类实施歧视或操纵；
- 不以删除现有风格换取新模型简化；
- 不通过简单截断制造“更短”；
- 不让模型自行修改联系人事实、关系事实或用户永久人格。
