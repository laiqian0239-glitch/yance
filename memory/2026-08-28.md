### A. Marker boundary / scope correction

Exact `electron/main.js` ordering was checked: `DesktopHost` (and therefore BackendProcessHost / BackendOwnerRegistry construction) occurs **before** the `runtime-identity-verified` log marker. Therefore constructor-time sync load/probe helpers are pre-marker and are not automatically marker→fork blockers. Do not waste time blindly asyncifying every sync compatibility helper.

After the marker, startup proceeds through the coordinator/DesktopHost into `BackendProcessHost._startUnlocked()`.

### B. Actual owner/fork ordering

At `0b491b` the real startup sequence is:

`async launch validation → async runtime probe → await startup admission lock → physical fork → await child PID → await process identity → await durable SPAWNED owner write → await admission release → write startup frame → credential/runtime startup`.

Never describe this as durable PID owner registration before physical fork.

The safety argument available for the current architecture is **lock-held-across-fork + durable-before-activation**:

- `backend/desktopHostedEntry.js` does not load boot restore/SQLite mutex/authorityWriteHost/runtime/server before receiving the DesktopHost startup frame.
- `readStartupFrame()` is async and bounded by timeout.
- Parent writes the durable SPAWNED owner record and releases admission before sending the startup frame.

This means a parent crash between physical fork and durable SPAWNED registration can leave an inert child waiting on the startup pipe, not an activated backend authority. This invariant must be made explicit and tested; redesign to a supervisor/reservation is unnecessary unless this invariant cannot be proven.

### C. Definite remaining same-root bugs

1. `BackendOwnerRegistry.updateAsync()` still falls back to synchronous `register(context)` when `this.record` is absent. Add/use a true `registerAsync()` and make `updateAsync()` call that async path. Do not allow post-marker async code to fall back into `_withOwnerClaimLock` / sync durable write.

2. `BackendOwnerRegistry.probeAsync()` is not truly non-blocking: it still calls synchronous `this.isProcessAlive(pid)`; production default ultimately uses `process.kill(pid, 0)`. Introduce a genuinely async production liveness probe for post-marker/recovery use (Windows can use bounded async process-query isolation). Test-injected synchronous collectors may remain test-only.

3. `BackendProcessHost._recoverRejectedOwnerForStartUnlocked()` PID-reuse branch currently calls `this.clearRejectedOwner({ force: true })` without `await`. This is a real async propagation bug. Must await the durable clear before reporting recovery success.

4. `BackendProcessHost._terminateOrphanOwner()` initially calls `probeAsync` but its `waitDead` loop repeatedly calls synchronous `ownerRegistry.probe(record)`. Convert the recovery polling loop to a true awaited async liveness path.

5. `BackendProcessHost.clearRejectedOwner()` fallback liveness check currently uses synchronous `ownerRegistry.probe(...)` when there is no exact observed child-exit proof. Use the true async probe and await it.

6. `_bindChildLifecycle` `onExit` remains a synchronous EventEmitter callback and still calls synchronous `ownerRegistry.markExited(...)` durable persistence. Do NOT merely make the event callback `async` and leak rejection. Build an explicit composite owner-exit recovery Promise that includes:
   - credential owner recovery,
   - awaited `markExitedAsync` when the exiting child owns the durable claim,
   - awaited admission release when exit occurs before claim registration.
   Store this Promise in `ownerExitRecoveryByChild`; existing `waitForOwnerExitRecovery(child)` becomes the fail-closed barrier. Attach rejection handling explicitly so no unhandled EventEmitter Promise exists.

7. The current pre-claim exit admission release in `onExit` is fire-and-forget (`Promise.resolve(admission.release()).catch(...)`). Include it in the same composite recovery Promise so startup/stop cleanup can observe its completion/failure.

8. `containRejectedOwner()` synchronously calls `ownerRegistry.probe(...)` while performing immediate authority revocation. Preserve immediate in-memory API/FD5/FD6 containment, but avoid OS liveness probing there:
   - if exact owned `ChildProcess` exists, derive liveness from in-memory child state;
   - if only restored/orphan durable state exists, fail closed as potentially live and defer real liveness to async recovery.

9. `DesktopCredentialApplicationCoordinator` has the same synchronous native liveness issue in `_backendChildLive()` / `_persistedContainmentPidLive()` when no exact child is available. Add async recovery variants for post-marker containment/recovery, and make release/cleanup paths await them. Keep exact owned-child memory checks synchronous.

10. `asyncDurability.atomicWriteJsonAsync()` has an invariant mismatch: directory fsync calls `fileSyncAsync(...)`, which already tolerates only approved directory errors, but an outer `catch (_) {}` currently swallows **all** remaining directory fsync failures. Remove that blanket catch so non-tolerated directory durability failures fail closed as documented. Because this touches shared durability, rerun only the relevant durability/atomicity focused test afterward; do not rerun the full credential suite.
